# Met6.
| Метод | Безопасен? | Идемпотентен? | Обоснование |
| :--- | :---: | :---: | :--- |
| **GET** | Да | Да | Повторный вызов GET /users/1 не меняет данные на сервере и возвращает один и тот же результат (проверено личным вызовом). |

| **PATCH** | Нет | Не всегда | Выведено из теории 2.3: обновление конкретного поля идемпотентно (name="Ada"), но операции вроде инкремента счетчика - нет. |
| **DELETE** | Нет | Да | Выведено из теории 2.3 и Met4: повторный вызов удаляет уже отсутствующий ресурс, но итоговое состояние системы не меняется. |

**Вопрос к себе:**

Ответ: Три строки (GET, POST, PUT) заполнены на основе личных практических наблюдений из задач Met1–Met5, а две строки (PATCH, DELETE) - выведены из теории раздела 2.3.

# Met7.

| Исходный адрес | Где записано действие | Нарушенный принцип REST | Верная пара «метод + путь» |
| :--- | :--- | :--- | :--- |
| /api/getUsers | В пути (getUsers) | Глагол в пути. Путь должен обозначать ресурс, а не действие. | GET /api/users |
| /api?action=deleteUser&id=5 | В query-параметрах (action=deleteUser) | Действие спрятано в query. Выглядит как безопасный GET в логах. | DELETE /users/5 |
| /users/5/remove | В пути (/remove) | Псевдоресурс. Путь прикидывается ресурсом, но является командой. | DELETE /users/5 |
| /posts/delete-all | В пути (delete-all) | Глагол/действие в пути вместо использования HTTP-метода. | DELETE /posts |

**Вопрос к себе**: Чем действие, спрятанное в query, опаснее глагола в пути?\
Ответ: Запросы с параметрами в query часто логируются прокси-серверами, провайдерами и сохраняются в истории браузера. Если там спрятано удаление или изменение данных, случайный переход по ссылке или повтор GET-запроса из истории может случайно выполнить опасную операцию.

# Met9.

C Accept (Accept: application/json):
  * Статус: 200 OK
  * Начало тела: {\n  "id": 1,\n  "name": "Leanne Graham"\

Без Accept:
  * Статус: 200 OK
  * Начало тела: {\n  "id": 1,\n  "name": "Leanne Graham"
*Изменилось:** Ничего не изменилось (ни статус, ни формат тела).
*Вывод:** Сервер/песочница не смотрел на заголовок Accept и по умолчанию отдаёт данные в формате JSON.

**Вопрос к себе:** Если по телу разницу не видно, где ещё в ответе она обязана проявиться?\
Ответ: В заголовке ответа Content-Type. В обоих случаях он вернул application/json; charset=utf-8.

# Met10.

* Content-Type: application/json -> Статус: 201 Created | Тело: {\n  "title": "T",\n  "body": "B",\n  "userId": 1,\n  "id": 101\n}
* Content-Type: text/plain -> Статус: 201 Created | Тело: {\n  "title": "T",\n  "body": "B",\n  "userId": 1,\n  "id": 101\n}
*Что изменилось между ответами:** Ответы полностью идентичны, статус и тело не изменились.
*Вывод:** Песочница не валидирует заголовок Content-Type и обрабатывает тело одинаково, независимо от того, указан ли application/json или text/plain.

**Вопрос к себе:** Одинаковые статусы - это «сервер не читает заголовок» или «сервер простил тебе странный заголовок»?\
Ответ: В данном случае песочница «простила» заголовок и распарсила JSON вопреки text/plain. Различить это помог бы заголовок ответа или тест с некорректным JSON-синтаксисом.

# Met11.

POST https://httpbin.org/get -> Статус: 405 Method Not Allowed\
GET https://httpbin.org/post -> Статус: 405 Method Not Allowed\
*Код «метод не подходит»:** 405 Method Not Allowed\
*Пришёл в запросе:** В обоих запросах (POST /get и GET /post).

**Вопрос к себе:** Для чего предназначен каждый из этих двух адресов по смыслу имени и почему сервер отказал?\
Ответ: Эндпоинт /get предназначен только для чтения методом GET, а /post - только для отправки данных методом POST. Сервер вернул 405, потому что отправленный HTTP-метод не поддерживается данным конкретным ресурсом.

# Met12.

## Анализ АПИ:
Сервис A:
  * Один адрес? **Да** (/api)
  * Методы по назначению? **Нет** (всегда POST)
  * Статусы со смыслом? **Нет**
  * Подсказки в ответе? **Нет**\
  **Уровень: 0**
  
Сервис B:
  * Один адрес? **Нет** (есть /users/1)
  * Методы по назначению? **Да** (GET, PUT, DELETE)
  * Статусы со смыслом? **Да** (200, 404)
  * Подсказки в ответе? **Нет**\
  **Уровень: 2**
  
Сервис C:
  * Один адрес? **Нет**
  * Методы по назначению? **Да**
  * Статусы со смыслом? **Да**
  * Подсказки в ответе? **Да** (приходят ссылки на связанные ресурсы)\
  **Уровень: 3**

**Обоснования**:\
A: Уровень 0, так как используется один эндпоинт /api, а вся логика и действия завязаны на JSON-тело.\
B: Уровень 2, так как выделены URI для ресурсов и используются стандартные HTTP-методы вместе со статусами ответов.\
C: Уровень 3, так как помимо адресов ресурсов и HTTP-методов ответы содержат гипермедиа-ссылки (HATEOAS).

**Вопрос к себе:** Что пришлось бы добавить в АРІ В, чтобы он поднялся на уровень выше, и что пришлось бы поменять в А?\
Ответ:
* В API B нужно добавить HATEOAS-ссылки в тело ответа (например, ссылки на редактирование, удаление или связанные сущности).
* В API A нужно полностью переработать архитектуру: разнести операции по отдельным URL-ресурсам (Уровень 1) и применить правильные HTTP-методы со статусами (Уровень 2).
